# Матчі, реєстрація стрільців і експорт у PractiScore (.psc)

**Статус:** план реалізації (квітень 2026). **Передумога:** перевірено імпорт згенерованого `.psc` у **PractiScore 2** v1.7.36 (Android); формат = **ZIP** з `match_def.json` + `match_scores.json`.

**Зв’язок:** [PORTAL_PLAN.md](./PORTAL_PLAN.md) (архітектура, Supabase), [TECH.md](./TECH.md); **архітектура модуля матчів і прогалини (техніка / право / продукт):** [MATCH_ADMIN_ARCHITECTURE.md](./MATCH_ADMIN_ARCHITECTURE.md) (зокрема **§8 — UX-орієнтир [practicarms.ua](https://practicarms.ua/)** під центр реєстрації). Інструменти для експериментів з `.psc`: `scripts/practiscore/`.

---

## 1. Цілі та межі MVP

### 1.1 Що будуємо

| Шар | Результат |
|-----|-----------|
| **Дані** | Обліковки, матч → склади → заявки стрільців; **підтвердження реєстрації та примітки про оплату** (вручну організатором); прив’язка до вправ Stage Builder |
| **Експорт** | Збірка **`.psc`**, сумісної з перевіреною версією PS (див. розділ 6); інструкція для MD на імпорт |
| **Паралельно** | Організатор проєктує вправи в Stage Builder; портал агрегує метадані для PS (раунди, очки попперів тощо) |

### 1.2 Що не обіцяємо в першій хвилі

- Офіційний **API PractiScore** або двостороння **синхронізація через PIN із сервером PS** без партнерської угоди.
- Автопідтягування **результатів** з PS на портал (лише посилання на опубліковані результати PS або ручний імпорт файлу, якщо з’явиться стабільний формат).
- **Онлайн-оплата через платіжні шлюзи** у першій хвилі — ні (достатньо ручного підтвердження організатором див. фазу B).

### 1.3 MVP: IPSC Shotgun

**(Рушниця.)** Перший реліз модуля реєстрації матчів і експорту **`.psc`** орієнтується лише на дисципліну **IPSC Shotgun** за відповідним rulebook IPSC.

**Чому так простіше:** один узгоджений пресет для «важких» частин `match_def` (дивізіони, процедури, мішені), менше гілок у формах і в PSC-мапері; тестовий імпорт уже пройдено на зразку shotgun-експорту (див. передумогу на початку документа та фікстуру `scripts/practiscore/fixtures/practiscore-roundtrip-test.psc`).

**Реалізація:** у базі та UI для MVP прийнятно фіксувати `discipline = shotgun` (або лише `ipsc_shotgun`) і не показувати перемикач інших дисциплін; зв’язок вправ із Stage Builder — за **`weaponClass: shotgun`** для сцен матчу.

**Після MVP:** додати handgun / PCC / rifle / mini rifle як окремі пресети та окремий грумінг.

### 1.4 Узгодження продукту: роллаут, ролі, приватність (квітень 2026)

1. **Не показуємо модуль матчів гостям основного прод-сайту**, доки не буде повної реалізації та регресійного тесту. Код і маршрути залишаються в репозиторії; на **основному прод-домені** маршрути матчів вимкнено **прапорцем збірки** `VITE_ENABLE_MATCH_PORTAL` (увімкнення: `1` / `true`; пор. нижче **§1.4а** та [TECH.md](./TECH.md)). Для розробки й службового доступу — окремий деплой **staging / preview** або інший хост із увімкненим прапором; згодом модуль можна вшити в портал без зміни базових URL (`/:locale/matches/…`).

2. **Дві ролі доступу (цільовий стан):** **організатор** і **стрілець**. Стрілець реєструється вільно й отримує календар / перелік матчів / публічну картку й реєстрацію на змагання. **Право створювати й вести матчі** — лише після **підтвердження власником порталу** (пізніше можлива оплата доступу). На рівні MVP/Supabase це вимагатиме окремої таблиці дозволів або поля в профілі + оновлення RLS (поки поза поточною міграцією BL-025).

3. **Приватність учасників (Україна / безпека):** має бути режим, у якому **повний список зареєстрованих стрільців** на публічній сторінці **не показується** — бачить лише організатор (політика на рівні матчу або профілю + RLS / RPC). Аноніми й інші стрільці не мають бачити імена без явної згоди / політики продукту.

4. **UX публічної картки** для стрільця — орієнтир на структуру на кшталт [картки змагання на practicarms.ua](https://practicarms.ua/event-10571-sunday-shotgun-match.html): назва, опис/вартість/реквізити в тексті, дата, місце, ліміт учасників, скводи, блок реєстрації, контакти організатора тощо — зіставити з нашими полями `matches.*` і markdown-описом.

5. **Скводи:** реалізуємо повний сценарій (CRUD, місткість, обмеження під ліміт матчу — валідація при імплементації A4/A5).

6. **Статус «скасовано» матчу:** у першій хвилі **не** робимо (лише `draft` / `published` та подальше редагування).

7. **Після публікації:** організатор може **продовжувати редагувати** поля матчу (без «локу» публікації), узгоджено з RLS.

### 1.4а Вмикання модулю в збірці

| Середовище | Поведінка |
|------------|------------|
| `vite dev` | За замовчуванням маршрути матчів **увімкнені**; вимкнути локально: `VITE_ENABLE_MATCH_PORTAL=0`. |
| Production (напр. shooters-tools.com) | Якщо `VITE_ENABLE_MATCH_PORTAL` **не** `1`/`true` — маршрути `/:locale/matches/*` **не реєструються**. |
| Staging / службовий URL | У змінних збірки або Vercel Environment: `VITE_ENABLE_MATCH_PORTAL=1`. |

Код: `isMatchPortalEnabled()` у `src/portal/featureFlags.ts`.

## 2. Архітектурні принципи

1. **Modular monolith** (як у [PORTAL_PLAN.md](./PORTAL_PLAN.md)): новий модуль маршрутів `features/match-admin` (назва умовна), без імпорту внутрішніх файлів Stage Builder в реєстрацію — лише **контракти** (`contracts/matchExport.ts` або аналог).
2. **Supabase:** Postgres (матч, заявки, скводи), RLS за `organizer_id` / ролями; **Auth** для організатора та стрільця; за потреби **Edge Function** для генерації `.psc` (не віддавати секрети на клієнт).
3. **Версіонування схем:** реєстраційні DTO і фрагмент `match_def` — з полем `schema_version`, щоб мігрувати без зламу старих записів.
4. **PSC як адаптер:** окремий шар `psc/` (Node або Python на CI/Edge): **вхід** — канонічна модель матчу порталу; **вихід** — bytes `.psc`. Клонер `psc_clone_test.py` залишається для регресій «як у зразку».

## 3. Модель даних (чернетка)

Таблиці / сутності (імена умовні; уточнити при міграціях):

| Сутність | Ключові поля |
|----------|----------------|
| `match_admin_profiles` | `user_id` (FK `auth.users`), `display_name` — у міграції [SUPABASE_MATCH_ADMIN.md](./SUPABASE_MATCH_ADMIN.md) |
| `matches` | `id`, `organizer_id`, назва, дата, локація, ліміт учасників, `discipline` (**MVP:** `shotgun` / ipsc shotgun; інші ipsc-дисципліни — після MVP), `ps_match_subtype` (мапінг на `match_type`/`match_subtype` у JSON PS), статус |
| `squads` | `match_id`, номер/ім’я, `start_time`, `capacity` |
| `registrations` | `match_id`, `user_id` або гість, `squad_id`, дивізіон, клас, PF, категорії, статус (`pending` / **`confirmed`** / `cancelled` — назви уточнити в міграції), **`payment_note`** (вільний текст, напр. «налічні 28.03»), **`confirmed_at`**, **`confirmed_by`** (організатор), timestamp подачі заявки |
| `payments` (опційно пізніше) | *У MVP немає.* Окремий запис під онлайн-оплату можна додати, коли з’явиться шлюз. |
| `match_stages` (посилання на вправи) | `match_id`, порядок, `stage_project_id` (посилання на збережений share / об’єкт storage), або вбудований snapshot метаданих для експорту |

**Реалтайм-список учасників:** Supabase Realtime на `registrations` для публічної сторінки матчу (лише неперсональні поля за політикою).

## 4. Фази реалізації

### Фаза A — Фундамент (бекенд + мінімальний UI)

- Увімкнути **Auth** (організатор / стрілець); таблиці `matches`, `squads`, `registrations`.
- CRUD матчу для організатора; публічна картка матчу (read-only).
- Заявка стрільця: вибір скводу з вільних слотів; збереження дивізіону / PF / класу (валідація під обрану дисципліну).

**Критерій готовності:** один тестовий матч у проді, 2–3 тестові заявки без підтвердження.

### Фаза B — Підтвердження реєстрації й облік оплати (без платіжних шлюзів)

- У картці матчу для організатора — перелік заявок з полями: **підтвердити участь**, **примітка про оплату** (довільний текст: «перерахування», «налічні», дата тощо).
- Орієнтовний потік: стрілець подає заявку → статус «очікує» → організатор за фактом отримання внеску (як він домовився з учасником поза сайтом) **підтверджує реєстрацію** й за потреби дописує примітку.
- У тексті матчу (опційно markdown) організатор публікує **реквізити й правила оплати** — поза платформою, без webhook’ів.

**Критерій:** організатор вручну перевів заявку в підтверджений статус; публічний список учасників показує лише підтверджених (або режим як у політики продукту).

**Пізніше (не MVP):** інтеграція платіжного провайдера — окремий епік за потреби.

### Фаза C — Зв’язок зі Stage Builder

- **Варіант 1 (швидший):** організатор вручну прикріплює **посилання на share** (`/v/:id`) на кожну вправу; бекенд тягне метадані через існуючий API share або зберігає snapshot при «прив’язці».
- **Варіант 2 (пізніше):** сутність «матчовий проєкт» з масивом stage ids у хмарі (потребує розширення BL-001 / окремий епік).

З `*.stage.json` (або API) вже можна рахувати: мін. постріли, типи мішеней, **поппери** — для мапінгу в `match_stages[]` PS.

**Критерій:** для N вправ на матчі є стабільні поля для експорту PS (назва вправи, Comstock/…, poppers, paper targets count, max points — згідно з тим, що читає PS для обраного `match_subtype`).

### Фаза D — Експорт `.psc`

- Реалізувати **мапер** канонічної моделі → `match_def.json` (мінімальний підтримуваний набір полів + копія з валідного зразка для «важких» блоків: `match_procs`, `match_dqs`, `match_pfs`, `match_custom_targets`, якщо потрібні для дисципліни).
- Генерувати `match_scores.json` з порожніми `match_scores` для «свіжого» експорту (як у `psc_clone_test.py`).
- Упакувати ZIP (Deflate), віддати файл з **Content-Disposition**; логувати `app_version` PS, з яким тестували.
- **Регресія:** після змін порівнювати з `scripts/practiscore/fixtures/practiscore-roundtrip-test.psc` на рівні структури (тест скриптом або Vitest через виклик WASM/не обов’язково для v1).

**Критерій:** MD завантажує `.psc` з портала на планшет і бачить вправи + стрільців як у тестовому сценарії.

### Фаза E — PDF «всі вправи»

- Серверний або клієнтський збірний PDF із існуючого PDF-експорту Stage Builder по кожній прив’язаній вправі; одна назва файлу для друку.

**Залежність:** стабілізувати список вправ і порядок (з Фази C).

### Фаза F — Результати (пізніший етап)

- Публічне поле «результати на PractiScore» (URL).
- Опційно: імпорт файлу результатів з PS у storage для аналітики — **лише після** дослідження формату експорту результатів із тієї ж версії PS.

## 5. Ролі й доступи

| Роль | Дії |
|------|-----|
| Організатор (після дозволу власника порталу) | CRUD матчу, скводи, перегляд **повного** списку заявок та ПІБ, **ручне підтвердження + примітка про оплату**, експорт `.psc`, PDF |
| Організатор (кандидат без дозволу) | *Пізніша імплементація:* обмеження на створення матчів, доки запис не затверджений власником (окрема міграція / RLS). |
| Стрілець | Після логіну: календар/перелік матчів, картка, подача заявки, **публічний склад** лише там, де політика матчу дозволяє; оплата **поза** платіжним модулем. У режимі «прихованого списку» стрілець **не** бачить повного реєстру інших учасників на публічній сторінці. |
| Анонім | Публічна картка матчу (обмежені поля за RLS та налаштуваннями приватності), без доступу до ПІБ складу там, де ввімкнено приховування |

RLS у Supabase обов’язковий перед production.

## 6. PSC / PractiScore: технічні обмеження

- Формат **не документований офіційно** як публічний API — оновлення **PractiScore 2** може зламати сумісність. План мітигації:
  - зберігати **зразок** робочого JSON від кожної цільової версії PS у `scripts/practiscore/fixtures/versioned/` (після оновлення застосунку на майданчику);
  - проганяти ручний імпорт або «smoke test» перед релізом експорту.
- Поля типу **`match_procs`** / **`match_dqs`** залежать від правил версії правилника — або тягнемо пресет з шаблону (як у клонованому експорті), або спрощуємо під **одну MVP-дисципліну: Shotgun** (див. [§1.3](#13-mvp-ipsc-shotgun)).
