# Беклог продукту (ідеї та напрямки)

**Карта розділів і шаблони («Матчі — фаза B — MA-B01»):** спочатку **[PLANNING_INDEX.md](./PLANNING_INDEX.md)**. Детальний беклог **модуля Матчі** (`MA-*`) — **[BACKLOG_MATCHES.md](./BACKLOG_MATCHES.md)**.

Єдине місце для **накопичення можливих фіч і змін**, які ще **не** затверджені як поточна робота. Сюди переносимо ідеї з обговорень, [USER_FEEDBACK.md](./USER_FEEDBACK.md) та внутрішнього планування; **періодично** (наприклад, раз на спринт або раз на місяць) — **грумимо**: уточнюємо формулювання, оцінюємо зусилля, **пріоритезуємо**, переносимо в роботу або явно відкладаємо.

**Скрізна нумерація:** усі пункти мають **один** лічильник **`BL-001` … `BL-999`** (префікс **BL** = backlog). Нові ідеї отримують **наступний вільний номер**. Розділи: **активний** беклог, **відкладено**, **архів** (знято з грумінгу, номер і текст зберігаються для історії).

**Модуль «Матчі»:** окремий беклог з нумерацією **`MA-<фаза><NN>`** — **[BACKLOG_MATCHES.md](./BACKLOG_MATCHES.md)** (фази A–F + R; зв’язок із **BL-025**… у зведеній таблиці нижче).

**Не плутати з:** поточний зміст продукту — [FUNCTIONALITY.md](./FUNCTIONALITY.md); реліз-ноти та версії — [VERSIONING.md](./VERSIONING.md).

## Як вести цей файл

| Поле | Зміст |
|------|--------|
| **ID** | **`BL-NNN`** — скрізний номер у всьому беклозі; для посилань у чатах і в USER_FEEDBACK. |
| **Статус** | `idea` — сирий запис; `candidate` — зрозуміло «що» і «навіщо»; `ready` — можна брати в спринт після рішення; `in progress` — в роботі; `done` — зроблено; `dropped` — свідомо не робимо / застаріло. |
| **Пріоритет** | `P0` … `P3` або `—` поки не голосували. Після грумінгу оновлювати. |
| **Джерело** | Напр. `USER_FEEDBACK`, обговорення 2026-04-08, внутрішнє. |

Після грумінгу варто коротко зафіксувати рішення в колонці **Примітки** (наприклад: «взяти в Q2», «зачекати на бекенд», «об’єднати з …»).

### Покроковий процес (без фантазій)

1. **Задачі в беклозі** — формулювання, ID, дата додавання (нижче).
2. **Оцінка** — окремий крок: T-shirt (S/M/L/XL) або людино-години; заповнюється колонка **Оцінка** після обговорення.
3. **Пріоритезація** — після оцінки: P0…P3 або порядок у шарі.
4. **Архітектура та техстек** — лише для обраних до реалізації пунктів; окремий документ або підрозділ після п. 3.

Якщо для пункту **не вистачає вимог** — не оцінюємо до уточнення; питання — у колонці **Питання / ризики**.

### BL-036 — межі площадки полігону

*Контекст:* полігонні тири (майже замкнений прямокутник, підкова ~360°, вузький прохід, два рубежі, дві галереї). Зараз подібну геометрію можна лише **обійти** через **контур штрафної зони** (**BL-019**) — це **плутає** користувача й дає **подвійну огорожу** в 3D (`PerimeterWoodWall` по `fieldSizeM` + лінії контуру).

**Продуктове рішення (узгоджено):**

| Питання | Рішення |
|---------|---------|
| Замінити прямокутне поле? | **Ні** як систему координат (`fieldSizeM`, сітка, clamp, PDF aspect). Прямокутник — **аркуш**; полігон — **опційний шар** «де фізично тир». |
| UX | **Окремий режим / блок «Площадка»**, не під «Штрафні зони» вправи. |
| Дані | Окреме поле в `*.stage.json` (напр. `platformBoundaries` / `rangeLayout`), **не** перевикористовувати UI/семантику `penaltyZoneSet` для площадки. Геометрію полігонів можна **шарити** з `penaltyZones.ts` (вершини, замикання ε 5 см). |
| 2D | **Тонка нейтральна** лінія (сірий/коричневий), **без** червоної заливки штрафної зони; перемикач видимості шару. |
| 3D | Якщо контур площадки **заданий** — **не** рендерити `PerimeterWoodWall` по прямокутнику; периметр 3D — **сегменти по контуру** (ті самі бруски/матеріал, що зараз по краю поля), з **розривом** на проході (фаза C). |
| Шум / «стіна в стіні» | **Одна видима межа** світу для очей: або прямокутник (як зараз), або контур площадки — **не обидві**. |
| Штрафні лінії етапу | **BL-019** лишається для **вправи** (foot fault на етапі); можуть збігатися з межею площадки, але **різні** інструменти й підписи. |
| PDF / камера | Опційно кадр і знімок по **bounding box** контуру (+ поля); опційно **«Підігнати поле під контур»** (зменшити `fieldSizeM` до рамки + відступ). |

**Фази (рекомендована черга):**

| Фаза | Зміст | Критерій прийняття |
|------|--------|-------------------|
| **A** | Прямокутник площадки: діалог ширина×довжина (м), позиція на плані → замкнений контур | Майже прямокутні тири без ручних 4+ кліків |
| **B** | Полігон по вершинах у режимі «Площадка»; збереження в JSON; 3D без подвійної стіни | Підкова / складний периметр; **немає** `PerimeterWoodWall` при наявному контурі |
| **C** | Прохід (ворота) на ребрі — розрив у лінії/3D, ширина в метрах | Вузький вихід без «зашитої шийки» вершинами |
| **D** | Кілька зон (`polygons[]`) + перехід; union для аналітики — пізніше, разом з **BL-010** за потреби | Дві галереї на одному файлі вправи |

**Відкрито на грумінг:** чи потрібна версія схеми `stage.json`; чи експортувати межу площадки в `.psc`; i18n UK/EN для блоку «Площадка».

**Зв’язок:** **BL-019** (геометрія полігонів), **BL-010** / **BL-013** (union допустимої зони — для **вправи**, не обов’язково для площадки на фазі A–B). **Не** замінює [PLAN_FIELD_PDF_GRID.md](./PLAN_FIELD_PDF_GRID.md) (розмір поля вже зроблено).

### BL-010 — специфікація (уточнення)

*Відмінність від поточного продукту:* зараз — один сектор безпеки від **стартової позиції** за кутами з брифінгу ([FUNCTIONALITY.md](./FUNCTIONALITY.md)). **BL-010** — **глибша логіка**: умовно для **кожної точки** простору в **допустимій області** за **BL-019** (**об’єднання** відокремлених штрафних зон, **отвори**, опційні старти або брифінг без маркера; до реалізації — наближені евристики), аналізувати:

1. Чи є **видимі мішені за межами кута безпеки 180°** (відносно напрямку стрільби / локальної орієнтації з цієї точки) — тобто «простріл» поза безпечним півколом.
2. З яких із цих точок мішень **не прикрита декораціями** (реквізит як перешкода для променя з точки до мішені) — щоб відрізнити «теоретично в секторі» від «реально прострелюється» з урахуванням щитів, бочок тощо.

*Реалізація:* окремий обчислювальний шар (дискретна сітка або вибірка точок уздовж межі зони, промені / кути на 2D-плані; за потреби — спрощені профілі висоти). Це **не** дублікат одного клину від старту, а **глобальніший** аналіз сцени.

**Відкрито для наступного грумінгу:** крок дискретизації точок; чи достатньо 2D-проєкції для першого MVP.

**Правила для перешкод (узгоджено):** окремо **розписати** набір правил на кшталт: щити **необмежені вгору** (як вони обрізають простір для променя) тощо — див. чергу питань п. **1**. Чернетка правил і план реалізації — **[VISIBILITY_AND_SAFETY_RULES.md](./VISIBILITY_AND_SAFETY_RULES.md)**.
